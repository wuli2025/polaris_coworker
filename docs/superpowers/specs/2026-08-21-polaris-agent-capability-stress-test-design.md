# Polaris Agent 能力全链路压测与完善设计

日期：2026-08-21

## 1. 目标

本次工作的被测对象是 Polaris 应用内部的底层 Agent，而不是模型 API 本身，也不是执行测试的 Codex 会话。测试必须证明用户从 Polaris 发起任务后，应用能否稳定地完成以下三类真实工作：

1. 浏览器任务：检索、阅读动态网页、多步导航、提取与核验信息、下载只读资料。
2. 代码任务：理解仓库、修复缺陷、实现功能、补测试、构建并交付可验证结果。
3. PPT 长任务：规划、分批生成、断点续跑、导出 PPTX，并保证页数、结构和可打开性。

测试同时覆盖 MiniMax 与 Kimi K3 两个供应商，重点评估 Polaris 的提示词装配、技能选择、工具执行、长任务编排、并发隔离、错误恢复、产物发现和前端状态收口。

## 2. 强制边界

- 所有被测任务必须从 Polaris 应用入口提交，走 `chat_send -> Polaris Agent -> 工具/技能 -> 产物` 链路。
- 测试控制器不得直接调用 MiniMax 或 Kimi 的 HTTP API，不得直接运行 Claude Code 来完成任务。
- 测试控制器不得代替 Polaris 打开网页、编写业务代码或生成 PPT；它只能启动/配置 Polaris、投递任务、监听事件、检查结果和收集指标。
- 供应商配置通过 Polaris 的 provider 命令写入和切换。MiniMax 使用 Anthropic 兼容地址 `https://api.minimaxi.com/anthropic`；Kimi K3 经 Claude Code 使用 Anthropic 兼容 Base URL `https://api.kimi.com/coding/`，模型为 `k3`。用户提供的 `/coding/v1` 仅用于 OpenAI 兼容客户端，不直接交给当前 Claude Code 链路。
- API 密钥只进入应用运行时配置或临时环境，不写入仓库、测试报告、快照和命令输出；所有错误与请求记录先脱敏再落盘。
- 浏览器任务保持只读。表单、上传、登录等有副作用的场景只允许针对本地或项目自有测试页面，不对第三方网站提交真实数据。
- 代码任务只允许修改为压测创建的隔离夹具仓库；不得让被测 Agent 修改 Polaris 主仓或用户其他项目。
- 不清理、覆盖或重置当前工作区已有未提交改动。修复若必须触及已修改文件，只做最小补丁并逐段检查差异。

## 3. 方案选择

### 方案 A：协议/API 直测

直接请求两家模型接口，测吞吐与输出质量。它速度快，但绕过 Polaris 的 Agent、技能、工具、长任务和前端状态，无法回答本次核心问题，因此不采用。

### 方案 B：纯 GUI 黑盒

只靠桌面点击和肉眼验收。它最接近最终用户，但重复性差、难以形成稳定指标，出错时也很难判断是模型、Agent、事件流还是界面问题，因此不单独采用。

### 方案 C：Polaris 应用入口驱动的混合全链路测试（采用）

通过 Polaris server/desktop 共用的数据面提交真实对话并监听 `chat:stream`，必要时用 GUI 复核关键体验。任务完全由 Polaris Agent 执行，控制器只做编排和客观验收。该方案既保留真实链路，又能重复、计时、并发和定位。

## 4. 架构与组件

### 4.1 测试控制器

新增一个只面向本项目的 Agent 压测入口，职责限定为：

- 检查 Polaris 健康状态与 Forge/浏览器前置能力；
- 通过应用命令创建专用项目和会话；
- 通过应用 provider 命令配置、切换供应商；
- 通过应用 `chat_send` 提交任务；
- 监听 WebSocket 事件，按 `req_id` 和 `conversation_id` 关联 delta、tool、artifact、error、done；
- 对无声、断流、异常退出和停滞进行有界等待；
- 汇总指标并生成脱敏 JSONL 与 Markdown 报告。

控制器不会包含任何完成浏览、编码或 PPT 制作的实现。

### 4.2 任务夹具

任务集按能力而非固定提示词堆数量，避免模型记忆和单一场景偏差：

- 浏览器：静态页面检索、动态渲染、多页导航、跨来源核验、页面结构变化、下载文件、反爬/超时降级。
- 代码：单文件缺陷、多文件功能、测试失败修复、类型错误、重构、陌生代码库导航、长输出与恢复。
- PPT：12 页基线、30 页中型、60 页长任务、中文商业汇报、数据故事、设计约束、多素材输入、途中失败续跑。

代码和有副作用的浏览器场景使用测试专属工作目录。每个任务有独立输入、期望条件、最大时长和清理规则。

### 4.3 结果判定器

判定器只检查 Polaris 的输出，不补做任务：

- 通用：收到唯一终态、无永远发送态、错误可理解、产物路径属于允许目录。
- 浏览器：工具确实被调用；答案包含要求的字段和来源；多来源事实一致；失败时给出可恢复原因。
- 代码：夹具测试/构建通过；变更范围符合任务；没有改动禁区；必要文件真实落盘。
- PPT：PPTX 是合法 ZIP/OOXML；页数符合任务；关系文件无断链；文本和关键章节存在；抽样渲染无全白页、严重裁切或重复页。
- 长任务：`polaris.build.json` 状态单调推进；失败后可从 checkpoint 续跑；完成后不残留 pending 单元。

### 4.4 报告

每次运行记录：供应商、场景、并发级别、请求轮数、首事件延迟、首正文延迟、总时长、工具调用数、错误类型、重试/续跑次数、产物判定和人工体验备注。报告提供供应商对比、失败聚类、可复现步骤、修复前后数据及仍受外部服务限制的事项。

## 5. 数据流

1. 控制器启动或连接 Polaris，执行健康检查。
2. 通过 Polaris 配置当前供应商并创建测试项目/会话。
3. 控制器提交任务；Polaris 内部完成 prompt/skill 注入、Agent 启动与工具执行。
4. 控制器只消费 Polaris 事件流，持续更新时间与状态机。
5. `done` 后检查会话历史、清单和产物；失败则保存脱敏证据。
6. 同一场景在另一供应商上以新会话重跑，避免会话上下文污染。
7. 汇总通过率与性能；对确定性缺陷创建回归测试并修复 Polaris。
8. 修复后从最低失败场景开始，再跑该域和跨域并发回归。

## 6. 分级负载

为保证今晚能形成有效结论，先正确性、后并发，不用大量错误请求消耗额度：

### 阶段 0：应用预检

- 两家供应商各跑一条短对话、一条工具调用和一条小产物任务。
- 浏览器、Node/Python、Forge、PPTX、WebSocket 与工作目录逐项确认。
- 任一预检失败先定位，不进入高并发。

### 阶段 1：能力矩阵

- 每家供应商至少覆盖浏览器 8 个、代码 8 个、PPT 6 个场景。
- 其中每家至少一项 60 页 PPT 和一项跨文件代码任务。
- 先串行运行，区分能力缺失与并发故障。

### 阶段 2：并发与长稳

- 独立会话并发按 `2 -> 4 -> 8` 提升，每级混合浏览器、代码和 PPT 任务。
- 只有上一档没有系统性失败才升档；429/配额限制按供应商分别退避，不算 Polaris 缺陷。
- 至少完成一次包含多个分批轮次的长任务续跑，以及一次取消后重新发起验证。

### 阶段 3：故障恢复

- 覆盖工具不存在、浏览器依赖缺失、网络超时、模型 4xx/5xx、流中断、产物不完整、清单停滞。
- 验证错误能收口到 `done`，UI 不永久转圈，用户能看懂下一步，并可从断点恢复。

## 7. 错误分类与修复策略

错误按责任层分类，避免把供应商问题误修成应用问题：

- `provider`：鉴权、模型名、协议、429、上游 5xx。
- `agent`：不遵循技能、工具选择错误、上下文或多轮状态丢失。
- `tool`：浏览器、文件、Shell、Forge 或依赖不可用。
- `orchestration`：事件错配、无终态、并发串台、停滞、取消/恢复失败。
- `artifact`：路径发现错误、文件损坏、页数/内容不完整。
- `ux`：状态文案不清楚、错误气泡误判、进度失真、完成后找不到产物。

只有能在 Polaris 链路稳定复现、且责任属于应用的缺陷才修改代码。每个修复先添加最小失败测试，确认红灯，再做单一修复并跑域内与全局回归。外部故障通过退避、清晰提示、熔断或降级处理，不伪装为成功。

## 8. 成功标准

- 两家供应商都能通过 Polaris 完成三类任务的基础场景。
- 串行能力矩阵的应用内失败均有明确归因；可修复的 P0/P1 问题全部有回归测试和修复。
- 并发运行不发生会话串台、请求事件错配、永久发送态、进程泄漏或主服务崩溃。
- 60 页 PPT 能分批推进并生成结构有效、页数正确的 PPTX；中断后能从清单继续。
- 代码任务只改夹具目录，并由夹具自带测试/构建证明结果。
- 浏览器任务由 Polaris 工具真实执行，失败不会被无来源的模型臆测冒充成功。
- 最终报告不含密钥，包含失败证据、修复清单、修复前后对比和未解决限制。

## 9. 非目标

- 不评测两家模型的通用聊天排行榜分数。
- 不直接压测供应商网关极限 QPS。
- 不对真实第三方账号执行登录、发布、购买、发送消息等操作。
- 不重构与本次失败无关的 Polaris 模块。
